## 11. 트랜잭션 - 개념, 커밋, 롤백, 전파
- **트랜잭션(Transaction)**: 데이터베이스에서 하나의 논리적 기능을 수행하기 위한 작업의 단위(쿼리를 묶는 단위)
- **커밋(Commit)**: 여러 쿼리가 성공적으로 처리되었다고 확정하는 명령어. 트랜잭션 단위로 수행되며 변경 내용이 영구 저장
- **롤백(Rollback)**: 트랜잭션으로 처리한 묶음 과정을 일어나기 전으로 되돌리는 일(취소)
- **트랜잭션 전파(Propagation)**: 여러 트랜잭션 관련 메서드의 호출을 하나의 트랜잭션에 묶이도록 하는 것. 커넥션 객체를 직접 넘기지 않아도 됨

## 12. 트랜잭션 - ACID
### 원자성(Atomicity)
"all or nothing". 트랜잭션과 관련된 일이 모두 수행되었거나 모두 수행되지 않았거나를 보장.

### 일관성(Consistency)
'허용된 방식'으로만 데이터를 변경해야 함.

### 격리성(Isolation)
트랜잭션 수행 시 서로 끼어들지 못함.

### 지속성(Durability)
성공적으로 수행된 트랜잭션은 영원히 반영되어야 함.

> **무결성**: 데이터의 정확성, 일관성, 유효성을 유지하는 것

## 13. 트랜잭션 격리성
트랜잭션은 무조건 서로 접근 불가일까? 그렇지 않다. 격리성은 여러 단계가 있으며, **격리성과 동시성은 반비례 관계**다.

- 격리성이 높으면 → 동시성 낮음 → 성능 저하
- 격리성이 낮으면 → 동시성 높음 → 동시성 문제 발생 가능

MySQL에서 단계 조정 명령:
```sql
SET SESSION TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
```

### 격리 수준 4단계
- SERIALIZABLE
- REPEATABLE_READ
- READ_COMMITTED
- READ_UNCOMMITTED

## 14. 격리수준에 따른 현상
### 팬텀 리드(Phantom Reads)
한 트랜잭션 내에서 동일한 쿼리를 2번 이상 보냈을 때 **조회 결과가 다른** 현상. 다른 행이 더 추가된 모습이 유령(phantom) 같다고 해서 팬텀리드.

### 반복 가능하지 않은 조회(Nonrepeatable Reads)
한 트랜잭션 내의 **같은 행**에 두 번 이상 조회가 발생했는데 그 값이 다른 것.

### 더티 리드(Dirty Reads)
하나의 트랜잭션이 다른 트랜잭션의 **아직 커밋되지 않은 데이터**를 읽는 현상. T1이 업데이트 후 롤백했음에도 T2는 이미 커밋된 데이터로 판단하게 됨.

## 15. 격리 수준 상세
### SERIALIZABLE
- 커밋된 데이터만 조회 가능
- 트랜잭션을 순차적으로 진행
- 여러 트랜잭션이 동시에 같은 행에 접근 불가
- **세 현상 모두 발생 안 함**

### REPEATABLE_READ
- 커밋된 데이터만 조회 가능
- 반복 조회 시 같은 행 보장 (수정 차단)
- **새로운 행 추가는 막지 않음** → 팬텀리드 발생 가능
- **MySQL 8.0 InnoDB의 기본값**

### READ_COMMITTED
- 커밋된 데이터만 조회 가능
- **PostgreSQL, SQL Server, Oracle의 기본값** (가장 많이 사용)
- 팬텀리드, 반복 가능하지 않은 조회 발생 가능

### READ_UNCOMMITTED
- 가장 낮은 격리 수준, 가장 빠름
- 다른 트랜잭션이 커밋하지 않은 정보도 읽을 수 있음
- 팬텀리드, 반복 가능하지 않은 조회, 더티리드 모두 발생 가능

### 격리 수준별 발생 가능 현상
| 격리 수준 | 더티 리드 | 반복 불가능 조회 | 팬텀 리드 |
|-----------|-----------|------------------|-----------|
| SERIALIZABLE | X | X | X |
| REPEATABLE_READ | X | X | O |
| READ_COMMITTED | X | O | O |
| READ_UNCOMMITTED | O | O | O |

## 16. 인덱스의 구조와 효율적인 이유
데이터베이스 인덱스는 데이터 접근(검색, 삽입, 삭제) 속도를 향상시키기 위한 데이터 구조다. **책의 색인**과 같은 원리로, 모든 페이지를 훑지 않고 색인으로 빠르게 위치를 찾는다.

### B-트리
보통의 데이터베이스에서 사용되는 인덱스 구조. 이진검색트리를 일반화한 자료구조로 2개 이상의 자식을 가진 노드를 허용한다.
- **탐색 평균 O(log N)**
- **대수 확장성** 특징
- MySQL, PostgreSQL, Oracle이 사용

#### B-트리의 주요 특징
1. 모든 리프노드들은 같은 레벨 (균형 잡힌 트리)
2. **차수**: 노드가 가질 수 있는 자식의 최대 수
3. 노드 내에 여러 키를 저장하고, 각 키는 자식 노드 사이의 값을 구분
4. 노드가 꽉 차면 분할, 사용량이 줄면 인접 노드와 병합

### 대수 확장성(Logarithmic Scalability)
트리 깊이가 리프 노드 수에 비해 매우 느리게 성장하는 특성. 4차 B-트리는 깊이가 1 증가할 때마다 최대 인덱스 항목 수가 4배씩 증가한다. 즉, **트리 깊이 10으로 100만 개의 레코드를 검색** 가능.

핵심 원리는 요소들을 선형 탐색하는 것이 아닌 트리를 이용해 "있을 법한 노드"를 기반으로 빠르게 찾는 것.

## 17. 인덱스 성능 최적화
### 1. 인덱스는 비용이다
1. **두 번 탐색하도록 강요**: 인덱스 리스트 → 컬렉션 순으로 탐색하므로 읽기 비용 발생. 불필요한 인덱스는 제거해야 함
2. **수정 시 함께 수정됨**: 컬렉션이 수정되면 인덱스도 수정. B-트리 높이 균형 조정 비용 + 분산 비용 발생

> 컬럼 크기가 클수록 인덱스 크기도 커지므로 작게 유지해 효율을 높여야 한다.

### 2. 항상 테스팅하라
인덱스 최적화는 도메인 특징에 따라 다르다. `EXPLAIN`으로 테스팅하며 시간을 최소화해야 한다.

```sql
EXPLAIN SELECT * FROM your_table WHERE your_column = 'some_value';
```

쿼리 실행 시 풀스캔을 하는지, 처리 행 수가 너무 많지 않은지 확인해야 한다.

### 3. 복합 인덱스 설정 방법
복합 인덱스는 **순서**가 중요하다.

1. **==(equal) 비교** 쿼리가 있다면 가장 먼저 설정
2. **정렬**에 쓰는 필드를 그 다음에 설정
3. **다중 값 출력**(<, >, BETWEEN)에 쓰는 필드를 그 다음에 설정
4. **카디널리티가 높은 순서**대로 설정 (예: age보다 email 먼저)

> **카디널리티**: 유니크한 값의 정도

## 18. 클러스터형 인덱스 vs 보조 인덱스
### 클러스터형 인덱스(Clustered Index)
- 유일성과 최소성을 가지는 기본키 중 하나로 설정
- **테이블당 한 개만 가능** (보통 테이블의 기본키)
- 데이터 페이지가 정렬되어 저장
- 인덱스 페이지 리프노드에 **데이터 페이지**가 들어가 있음
- 탐색이 빠르지만, **삽입/삭제/수정이 느림** (테이블 재정렬 필요)
- 인덱스 순서와 데이터 순서가 일치

### 보조 인덱스(Non-clustered Index)
- 한 개가 아닌 **여러 개 생성 가능**
- 인덱스 페이지 리프노드에 데이터가 아닌 **데이터 페이지에 대한 포인터** 저장
- 정렬되어 있지 않아 탐색은 느리나, **삽입/삭제/수정이 빠름**
- 인덱스 순서와 데이터 순서가 일치하지 않음
- 보통 복합키(compound key)는 보조 인덱스로 만듦

### 생성 방법
- 클러스터형 인덱스: `PRIMARY KEY`, `ALTER TABLE ADD PRIMARY KEY`
- 보조 인덱스: `CREATE INDEX`, `ALTER TABLE ADD INDEX`

> 주의: `PRIMARY KEY`로 설정한다고 항상 클러스터형 인덱스가 되는 건 아님. SQL Server에서는 `PRIMARY KEY NONCLUSTERED`로 보조 인덱스로 설정 가능. 데이터베이스마다 생성 방법이 다르다.

## 19. 데이터베이스 정규화 - 개념과 이상현상
### 정규화 과정
릴레이션 간의 잘못된 함수 종속 관계로 인한 이상 현상을 해결하고, 저장 공간을 효율적으로 사용하기 위해 릴레이션을 여러 개로 분리하는 과정.

### 이상현상(Anomaly)
잘못된 DB 설계로 데이터 중복이 발생해 삽입/갱신/삭제 시 부작용이 생기는 것.

#### 삽입 이상
불필요한 데이터도 같이 삽입해야 하는 문제. 예) 이벤트 참여하지 않은 신규 회원 등록 시 이벤트번호, 당첨여부가 NULL이 됨

#### 갱신 이상
중복 레코드 중 일부만 변경되어 데이터 불일치. 예) 회원 등급 승급 시 일부 레코드만 수정됨

#### 삭제 이상
레코드 삭제 시 필요한 데이터까지 함께 삭제됨. 예) 이벤트 참여 취소 시 고객 정보까지 삭제됨

> 이러한 이상현상을 해결하는 척도가 **함수 종속**이며, 이를 기반으로 릴레이션을 분리하는 정규화 과정을 진행한다.

## 20. 함수적 종속성
**함수적 종속성(Functional Dependency)**: 어떤 릴레이션의 속성 부분집합이 X, Y일 때, 하나의 X에 대해 Y가 하나라면 X가 Y를 함수적으로 결정한다(또는 Y가 X에 함수적으로 종속).
- **X**: 결정자
- **Y**: 종속자

예) 아이디 → 이름, 아이디 → 등급
- 표현: `아이디 -> {이름, 등급}`

속성 자체의 특성을 기반으로 결정해야 한다. 기본키나 후보키가 아니더라도 결정자 X가 될 수 있다.

### 완전 함수 종속 vs 부분 함수 종속
- **완전 함수 종속**: Y가 X 전체에 종속됨
- **부분 함수 종속**: Y가 X 일부에 종속됨

예) `{아이디, 이벤트번호} → 당첨여부`, `아이디 → 이름`
- 이름은 아이디에 **완전 함수 종속**
- 이름은 {아이디, 이벤트번호}에 **부분 함수 종속** (아이디에만 완전 종속이므로)

## 21. 제 1정규형
릴레이션의 모든 도메인이 더 이상 분해될 수 없는 **원자 값(atomic value)** 만으로 구성되어야 한다. 한 개의 기본키에 대해 두 개 이상의 값을 가지는 반복 집합이 있다면 제거.

**변경 전 (반복 집합 있음)**
| 아이디 | 이벤트번호 | 당첨여부 |
|--------|------------|----------|
| zagabi | 221006-1, 221006-2, 221006-3 | Y, N, Y |

**변경 후 (원자 값으로 분리)**
| 아이디 | 이벤트번호 | 당첨여부 |
|--------|------------|----------|
| zagabi | 221006-1 | Y |
| zagabi | 221006-2 | N |
| zagabi | 221006-3 | Y |

## 22. 제 2정규형
제1정규형이면서, 기본키가 아닌 **모든 속성이 기본키에 완전 함수 종속**된 상태.

예) 기본키 {아이디, 이벤트번호}일 때 `등급`은 `아이디`에만 종속(부분 함수 종속) → 분리해야 함

**분리 결과**:
- 이벤트 릴레이션: `{아이디, 이벤트번호, 당첨여부}`
- 고객 릴레이션: `{아이디, 이름, 등급, 할인율}`

> **무손실 분해**: 분해한 릴레이션을 조인했을 때 분해 전 릴레이션으로 복원 가능해야 함

## 23. 제 3정규형
제2정규형이고, 기본키가 아닌 모든 속성이 기본키에 **이행적 함수 종속(Transitive Functional Dependency)을 만족하지 않는** 상태.

### 이행적 함수 종속
A → B, B → C가 존재할 때 논리적으로 A → C가 성립하는 관계.

예) `아이디 → 등급`, `등급 → 할인율`이면 `아이디 → 할인율`이 성립 (이행적 함수 종속)

**분리 결과**:
- 고객 릴레이션: `{아이디, 등급}`
- 고객 등급 릴레이션: `{등급, 할인율}`

## 24. 보이스/코드 정규형 (BCNF)
제3정규형이고, **모든 결정자가 후보키인 상태**. 하나의 릴레이션에 여러 후보키가 있을 때 제3정규형보다 엄격한 제약을 건 것.

### 예시 상황
- 각 수강명에 대해 한 학생은 오직 한 강사의 강의만 수강
- 각 강사는 한 수강명만 담당
- 한 수강명은 여러 강사가 담당 가능

후보키: `{학번, 수강명}` 또는 `{학번, 강사}`

여기서 **강사**는 후보키가 아님에도 **수강명을 결정**하는 결정자 역할을 한다. 새로운 강사 등록 시 학번이 NULL이 되는 삽입 이상 발생.

**BCNF 분해**:
- `{학번, 강사}` 릴레이션
- `강사 → 수강명` 릴레이션

### 정규화 과정 정리
| 단계 | 조건 |
|------|------|
| 1NF | 모든 속성이 원자 값 |
| 2NF | 1NF + 부분 함수 종속 제거 |
| 3NF | 2NF + 이행적 함수 종속 제거 |
| BCNF | 3NF + 모든 결정자가 후보키 |

> 이외에 고급 정규형 4NF, 5NF도 있다.

### 정규화는 꼭 필요한가?
정규화는 릴레이션을 나누는 과정이지만, 나누면 **조인 비용**이 늘어 성능이 나빠질 수도 있다. 서비스 특성에 따라 정규화 또는 비정규화를 선택해야 한다.

- **정규화 장점**: 중복 데이터 제거 → 메모리 요구량 감소, 오류 가능성 감소
- **정규화 단점**: 조인이 많이 필요한 쿼리에서는 성능 저하

> 조인은 코스트가 크다. 테이블 X(N개)와 Y(M개) 조인 시 최대 N*M 임시 테이블이 생성된다.

## 25. RDBMS vs NoSQL
| 기능/특징 | RDBMS | NoSQL |
|-----------|-------|-------|
| 스키마 | 엄격하고 정의되어야 함 | 유연하고 동적 변경 가능 |
| 쿼리 언어 | SQL | JSON, API, Cypher 등 다양 |
| 트랜잭션 | 지원 | 지원 |
| 기본 격리성 | repeatable_read (MySQL) | read_uncommitted (MongoDB) |
| 스케일링 | 수직 스케일링 (서버 성능 향상) | 수평 스케일링 (서버 대수 증가) |
| 예시 | MySQL, Oracle, PostgreSQL | MongoDB, Redis, ElasticSearch, Neo4j |

## 26. MongoDB의 특징과 주의점
MongoDB는 JSON으로 데이터에 접근하고 **BSON(Binary JSON)** 으로 저장되는 도큐먼트 기반 DB. 스키마를 정해놓지 않고 유연하게 삽입 가능해 다양한 도메인 분석/로깅 구현에 강점.

### MongoDB 주요 특징
#### 1. 기본키: ObjectID(_id)
도큐먼트 생성 시마다 자동 생성되는 유니크한 값. 구성:
- 유닉스 타임스탬프 (4바이트)
- 랜덤 값 (5바이트)
- 카운트 (3바이트)

#### 2. BSON
- 클라이언트-서버 간 통신: JSON
- 내부 저장/처리: BSON (JSON의 이진 확장 형식)
- 추가 데이터 타입 지원, 효율적 저장 가능

#### 3. 확장성
**샤딩**을 통한 수평적 확장 지원. 데이터를 여러 서버에 분산시켜 단일 서버 부하 감소.

#### 4. 2차원 좌표 인덱싱
**2D sphere index**로 2차원 좌표 인덱싱 가능 (위치 기반 검색에 유용)

#### 5. 트랜잭션 관련 기능
- **체크포인트**: 60초 간격으로 생성. 종료 시 마지막 유효 체크포인트에서 복구 가능
- **저널링**: 체크포인트 간 모든 데이터 수정 사항 유지. 중간 종료 시 저널로 재생산 가능

### MongoDB 사용 시 주의점
#### 1. 크기
RDBMS와 달리 스키마 없이 저장하므로, **칼럼 이름도 매번 바이트에 추가**된다. key-value 형태로 저장될 때 key 길이도 매번 저장된다.

예) `comments: string` 타입으로 저장하면 'comments'라는 8바이트가 각 도큐먼트마다 추가됨

#### 2. 메모리
WiredTiger 스토리지 엔진은 시스템 메모리 중 일부를 캐시로 사용:
- 공식: `0.5 * (전체 RAM - 1GB)`
- 최소 캐시: 256MB

**예시**:
- 4GB RAM: `0.5 * (4GB - 1GB) = 1.5GB`
- 1.25GB RAM: `0.5 * (1.25GB - 1GB) = 128MB` → 최소값 규칙에 의해 256MB

## 27. MySQL 스토리지 엔진: InnoDB vs MyISAM
| 특성 | InnoDB | MyISAM |
|------|--------|--------|
| 트랜잭션 지원 | 지원 | 미지원 |
| 락 및 동시성 | 행 레벨 락 | 테이블 레벨 락 |
| 외래 키 제약 | 지원 | 미지원 |

InnoDB는 MySQL 8.0의 기본 스토리지 엔진이며, 트랜잭션과 롤백을 지원한다. MyISAM은 트랜잭션을 지원하지 않아 `ROLLBACK`을 시도해도 삽입된 데이터가 그대로 남는다.

엔진 확인:
```sql
SHOW TABLE STATUS LIKE 'example_myisam';
```

## 28. 데이터베이스 데드락과 해결 방법
### 데드락(Deadlock)
둘 이상의 트랜잭션이 서로가 잠금을 포기하기를 기다리는 상황 (교착 상태와 동일 개념).

예) Transaction A는 accounts 테이블 락을 갖고 order 테이블 행을 요구, Transaction B는 order 테이블 락을 갖고 accounts 테이블 행을 요구 → 무한 대기

### 데드락 발생 조건 (4가지 동시 충족 시)
- **상호 배제**: 자원은 한 번에 하나의 트랜잭션만 사용
- **점유 및 대기**: 자원을 점유하면서 다른 자원을 추가 요구
- **비선점**: 점유한 자원을 강제로 빼앗을 수 없음
- **순환 대기**: 각 트랜잭션이 순환적으로 다른 트랜잭션이 점유한 자원을 대기

### 해결 방법 - 데드락 탐지
#### 1. Timeout
일정 시간 이후 트랜잭션이 실행되지 않으면 롤백.
- **장점**: 구현 간단, 빠른 해결
- **단점**: 타임아웃 설정이 어려움. 너무 짧으면 불필요한 중단, 너무 길면 해결 지연. 데드락이 아닌 경우에도 중단될 수 있음

#### 2. Wait for Graph
트랜잭션 대기 그래프를 만들고 사이클 발생을 주기적으로 검사.
- 대규모 DB에서는 사이클 탐지 비용이 큼

### 해결 방법 - 데드락 방지
#### 1. 격리 수준 변경
예) REPEATABLE_READ → SERIALIZABLE. 단, SERIALIZABLE이 아닌 이상 모든 데드락 제거는 불가능

#### 2. 자원 할당 순서 지정
서비스 로직 구축 시 자원 할당 순서를 일관성 있게 변경. 예) 항상 accounts → order 순으로 락 획득

#### 3. Wait-Die 방법 (비선점기법)
타임스탬프 기반으로 오래된 트랜잭션이 더 높은 우선순위를 가진다고 판정.
- 더 오래된 트랜잭션 = 더 작은 타임스탬프

**작동 방식 (T5, T10 예시, T5가 더 오래됨)**:
- **Wait**: 우선순위 높은 T5가 T10이 점유한 자원 요청 → T5는 **대기**
- **Die**: 우선순위 낮은 T10이 T5가 점유한 자원 요청 → T10은 **롤백**되고 재시도

#### 4. Wound-Wait 방법 (선점기법)
같은 타임스탬프 기반이지만 선점이 일어남.

**작동 방식 (T5, T10 예시, T5가 더 오래됨)**:
- **Wound**: T5가 T10이 점유한 자원 요청 → T10을 **부상**시켜 자원을 강제 해제하고 T5에 넘김
- **Wait**: T10이 T5가 점유한 자원 요청 → T10은 T5가 끝날 때까지 **대기**

### Wait-Die vs Wound-Wait 비교
| 방법 | 오래된 T가 새 T 자원 요청 | 새 T가 오래된 T 자원 요청 |
|------|---------------------------|---------------------------|
| Wait-Die (비선점) | 대기 | 롤백(die) |
| Wound-Wait (선점) | 부상(wound, 빼앗음) | 대기 |
