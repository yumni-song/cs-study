## 1. 데이터베이스의 기본 - 엔터티, 릴레이션, 속성, 도메인
### 데이터베이스의 정의와 특징
데이터베이스(DB)는 일정한 규칙으로 구조화되어 저장되는 데이터의 모음이며, 이를 관리하는 시스템을 DBMS(DataBase Management System)라고 한다. DBMS에 정의된 쿼리 언어를 통해 데이터에 CRUD가 가능하다.

데이터베이스의 주요 특징은 트랜잭션, 동시공유, 사용자별 데이터 접근 권한 부여, 데이터 암호화, 백업 및 복구 등이 있다.

### 엔터티(Entity)
사람, 장소, 물건, 사건, 개념 등 여러 속성을 지닌 명사이자 실제 세계의 객체를 데이터베이스에서 모델링한 것. DB 내에서 고유하게 식별될 수 있는 속성들을 가진다.

#### 약한 엔터티 vs 강한 엔터티
- **강한 엔터티(Strong Entity)**: 자체 기본키를 가지고 독립적으로 존재할 수 있음. 예) 학생
- **약한 엔터티(Weak Entity)**: 독립적으로 존재할 수 없고 강한 엔터티에 의존. 자체 주요 키가 없으며 관련 강한 엔터티의 키를 참조. 예) 강의 등록(학생과 강의에 종속)

### 릴레이션(Relation)
데이터베이스에서 정보를 구분하여 저장하는 기본 단위이자 엔터티의 집합과 속성을 표현하는 구조. 엔터티가 데이터베이스에 올라가면 릴레이션이 된다.

- **관계형 데이터베이스**: 테이블이라고 부름
- **NoSQL 데이터베이스**: 컬렉션이라고 부름

> RDBMS와 NoSQL 구조 차이 (MySQL vs MongoDB):
> - MySQL: 레코드 → 테이블 → 데이터베이스
> - MongoDB: 도큐먼트 → 컬렉션 → 데이터베이스

### 속성과 도메인
- **속성(Attribute)**: 릴레이션에서 관리하는 구체적이며 고유한 이름을 갖는 정보. 예) 차 엔터티의 차넘버, 바퀴수, 색깔
- **도메인(Domain)**: 속성이 가질 수 있는 값의 집합. 예) 성별 속성의 도메인은 {남, 여}

## 2. 필드, 레코드, 타입
엔터티가 데이터베이스에 들어갈 때 엔터티의 속성은 테이블의 필드로 들어가 이름, 타입으로 변환된다. 보통 한글 대신 영어 필드명을 사용한다.

### 필드와 레코드
필드를 가진 데이터들이 행 단위로 쌓이게 되며, 이를 **행(row), 레코드, 튜플**이라고 부른다.

### 숫자 타입
MySQL은 숫자 타입을 세분화하여 지원한다.

| 타입 | 바이트 | Signed 범위 | Unsigned 범위 |
|------|--------|-------------|----------------|
| TINYINT | 1 | -128 ~ 127 | 0 ~ 255 |
| SMALLINT | 2 | -32,768 ~ 32,767 | 0 ~ 65,535 |
| MEDIUMINT | 3 | -8,388,608 ~ 8,388,607 | 0 ~ 16,777,215 |
| INT | 4 | -21억 ~ 21억 | 0 ~ 약 42억 |
| BIGINT | 8 | -2⁶³ ~ 2⁶³-1 | 0 ~ 2⁶⁴-1 |

> MongoDB는 string, number처럼 단순한 타입만 지원한다.

### 날짜 타입
- **DATE**: 날짜만, 3바이트. 예) `2024-12-01`
- **DATETIME**: 날짜 + 시간, 8바이트. 예) `2024-12-01 12:00:01`
- **TIMESTAMP**: 날짜 + 시간, 4바이트, 1970-01-01 00:00:01부터 카운트한 값

## 3. CHAR와 VARCHAR의 차이
### CHAR
- 테이블 생성 시 선언한 길이로 **고정**
- 길이 범위: 0 ~ 255
- 선언한 길이만큼 항상 고정해서 저장

### VARCHAR
- **가변 길이** 문자열
- 길이 범위: 0 ~ 65,535
- 입력된 데이터에 따라 용량을 가변시켜 저장
- 예) `VARCHAR(10000)`이라도 실제 데이터가 10자라면 데이터 10바이트 + 길이 기록 1바이트로 저장
- 길이가 255 초과 시 길이 기록에 2바이트 사용

> 유동적인 데이터 → VARCHAR, 고정적인 데이터 → CHAR

### VARCHAR 최대 길이 설정 시 주의점
1. MySQL 행의 최대 크기는 65,535바이트
2. MySQL 5.5.3부터 utf8mb4 인코딩 지원 (이모지 4바이트, 한글 3바이트 커버)
3. 괄호 안 숫자는 바이트가 아닌 **길이 제한**

## 4. TEXT와 BLOB
### TEXT
- 최대 65,535개 길이의 텍스트 데이터 저장 가능
- TINYTEXT(255), MEDIUMTEXT(1,600만), LONGTEXT(40억) 등 다양한 종류

### VARCHAR vs TEXT 비교
| 항목 | VARCHAR | TEXT |
|------|---------|------|
| 저장 위치 | 행 내부(메모리) | 행 외부(디스크), 내부에는 포인터(8바이트)만 |
| max size limit | 가능 (최대 65,533) | 불가능 |
| 인덱스 | 바로 가능 | 크기 제한해야 가능 |
| 읽기 성능 | 좋음 | 좋지 않음 |

TEXT에 인덱스를 걸 때는 접두사 크기 제한이 필요하다:
```sql
CREATE INDEX idx_content ON board (content(20));
```

> MySQL에서 TEXT 컬럼에도 LIKE 함수 사용 가능

### BLOB
- 이진 데이터(Binary Object) 저장용 타입. 이미지, 오디오, 비디오 등
- 실제로는 잘 쓰지 않고, **이미지 호스팅 서비스(S3) 등에 올리고 URL을 VARCHAR로 저장**하는 게 일반적

#### BLOB을 잘 안 쓰는 이유
1. **성능 문제**: 큰 이진 파일 저장 시 DB 성능 저하, 백업/복구 시간 증가
2. **보안 문제**: 이미지 접근 제어와 보안 정책 적용이 복잡

## 5. ENUM과 SET
### ENUM
- 열에 할당 가능한 값의 리스트를 정의
- **단일 선택**만 가능
- 내부적으로 숫자로 저장되지만 사용자에게는 문자열로 표시 (red:0, green:1, blue:2)
- 최대 65,535개 요소

```sql
CREATE TABLE shirts (
    id INT NOT NULL AUTO_INCREMENT,
    color ENUM('red', 'green', 'blue') NOT NULL,
    PRIMARY KEY (id)
);
```

### SET
- ENUM과 비슷하지만 **여러 값을 동시에 저장 가능**
- 비트 단위 연산 가능
- 최대 64개 요소

```sql
INSERT INTO socks (colors) VALUES ('red,green'), ('green,blue');
```

> ENUM/SET은 공간 효율이 좋지만, 애플리케이션 수정 시 매번 DB 리스트를 수정해야 하는 단점이 있다.

## 6. 관계와 키
### 관계의 종류
- **1:1 관계**: 회원가입 시 유저당 이메일
- **1:N 관계**: 쇼핑몰 유저당 장바구니 상품들
- **N:M 관계**: 학생과 강의의 관계. 직접 연결하지 않고 중간 테이블을 두어 1:N, 1:M으로 분리

### 키의 종류
키는 테이블 간 관계를 정의하는 데 사용된다.

#### 1. 기본키(Primary Key, PK)
- **유일성과 최소성**을 만족
- 테이블의 각 행을 고유하게 식별
- 각 테이블에 하나만 존재 (조합 가능)
- 보통 'ID'나 '번호' 필드

##### 자연키(Natural Key)
- 데이터에 이미 존재하고 의미가 있는 필드를 사용
- 예) 주민등록번호, 차량번호
- **언젠가는 변할 수 있는 속성**이라 문제 발생 가능

##### 인조키(Surrogate Key)
- 식별을 위해 특별히 생성된 키 (보통 숫자, AUTO_INCREMENT)
- 실질적 의미 없음
- **일반적으로 인조키를 더 선호**

#### 2. 외래키(Foreign Key, FK)
- 다른 테이블의 기본키를 참조하는 필드
- 참조 기본키 값과 일치해야 함
- 중복 가능, NULL 가능

#### 3. 후보키(Candidate Key)
기본키가 될 수 있는 후보로, 유일성과 최소성을 만족하는 키

#### 4. 대체키(Alternate Key)
후보키 중 기본키로 선택되지 않은 키

#### 5. 슈퍼키(Super Key)
유일성만 갖춘 키 (최소성은 X)

#### 6. 복합키(Composite Key)
두 개 이상의 필드를 조합하여 만든 키. 각 필드 단독으로는 식별 불가하지만 조합 시 식별 가능

> **유일성**: 중복되는 값이 없음 / **최소성**: 최소 필드만 써서 키를 형성

## 7. ERD (Entity Relation Diagram)
ERD는 데이터베이스 구축의 기초 뼈대 역할로, 릴레이션 간 관계를 정의한다. 시스템 요구 사항을 기반으로 작성되며 이를 토대로 데이터베이스를 구축한다.

### 예시: 주문 시스템
- 영업사원은 0~N명의 고객을 관리
- 고객은 0~N개의 주문 가능
- 주문에는 1~N개의 상품 포함

주문과 상품은 N:M 관계인데, 구현 시에는 **OrderDetail** 같은 중간 매개체 테이블로 1:N, 1:M으로 분리한다.

```sql
-- 주문 세부 정보 (N:M 관계 해소)
CREATE TABLE Order_Details (
    OrderID INT,
    ProductID INT,
    Quantity INT,
    FOREIGN KEY (OrderID) REFERENCES Orders(OrderID),
    FOREIGN KEY (ProductID) REFERENCES Product(ProductID),
    PRIMARY KEY (OrderID, ProductID)
);
```

> `PRIMARY KEY (OrderID, ProductID)`는 **복합 기본키**로, 두 컬럼 조합으로 각 행을 고유하게 식별한다.

## 8. 조인 - 내부조인과 외부조인
조인(Join)은 두 개 이상의 테이블을 연결하여 데이터를 탐색하는 방법이다.
- MySQL: `JOIN` 쿼리
- MongoDB: `lookup` 쿼리

### 내부 조인(Inner Join)
두 테이블에서 일치하는 데이터만 반환 (**교집합**)

### 외부 조인(Outer Join)
- **왼쪽 외부 조인(Left Outer Join)**: 왼쪽 테이블의 모든 레코드 + 오른쪽의 일치 레코드. 일치 없으면 NULL
- **오른쪽 외부 조인(Right Outer Join)**: 오른쪽 테이블의 모든 레코드 + 왼쪽의 일치 레코드
- **전체 외부 조인(Full Outer Join)**: 양쪽 모든 레코드 반환, 일치 없는 부분은 NULL

> MySQL은 Full Outer Join을 지원하지 않아 `UNION`으로 처리해야 한다.

### 성능
일반적으로 **Inner Join이 Outer Join보다 빠르다**. 양쪽에서 일치하는 행만 필요로 하므로 처리 데이터가 적기 때문. 다만 실제 성능은 쿼리, DB 구조, 인덱스에 따라 다르다.

### Left Outer Join을 써야 할 때
일치하는 데이터가 없는 경우에도 결과를 보고 싶을 때. 예) 모든 회원 목록 + 팀 정보(팀이 없는 회원도 포함)

## 9. 교차조인과 자연조인
### 교차 조인(Cross Join)
- 두 테이블의 모든 행 조합을 생성 (**카테시안 곱**)
- 조인 조건이 없을 때 사용
- 3행 × 3행 = 9행 결과
- **성능이 매우 나쁨** → POC나 테스팅 시 사용, 보통 LIMIT 설정

```sql
SELECT Products.ProductName, Colors.ColorName
FROM Products
CROSS JOIN Colors;
```

### 자연 조인(Natural Join)
- 두 테이블 간 **동일한 이름의 모든 열**을 기반으로 자동 조인
- 명시적 조인 조건 불필요
- 이름이 같은 모든 열에 대해 Inner Join 수행

```sql
SELECT *
FROM Customers
NATURAL JOIN Orders;
```

### 성능 비교
자연 조인은 교차 조인보다 훨씬 적은 행을 반환하므로 보통 더 좋다. 데이터를 간단히 통합할 때 쓴다.

## 10. 조인 알고리즘
MySQL에서 특정 조인 알고리즘을 명시적으로 설정하는 것은 직접적으로 불가능하다. **쿼리 옵티마이저(query optimizer)**가 자동으로 가장 성능 좋은 알고리즘을 결정한다. (MySQL, PostgreSQL, Oracle, SQL Server 동일)

힌트 설정은 가능:
```sql
SET optimizer_switch="hash_join=off";
```

### 중첩 루프 조인(Nested Loop Join)
한 테이블의 각 행에 대해 다른 테이블의 모든 행을 순차적으로 검사해서 조인하는 방법.

```python
for rowA in tableA:
    for rowB in tableB:
        if rowA['id'] == rowB['id']:
            # 조인 수행
```

- **시간 복잡도**: O(M*N)
- **성능**: 소규모 데이터셋에 적합, 큰 테이블에는 비효율적

> **블록 중첩 루프 조인(BNL)**: 한 테이블의 블록을 메모리(조인 버퍼)에 한번에 로드 후 다른 테이블 행과 비교하는 발전된 방식

### 정렬 병합 조인(Sort Merge Join)
조인할 필드 기준으로 두 테이블을 각각 정렬한 후, 정렬된 순서에 따라 병합하여 조인.

- **시간 복잡도**: O(M log M + N log N)
- **성능**: 데이터가 이미 정렬되어 있을 때 효율적. 비등가 조인(`<`, `>`, `<=`, `>=`)에 효율적

> 자주 쓰이는 조인 조건에 맞게 데이터를 미리 정렬하거나 인덱스를 구성하면 성능 향상 가능

### 해시 조인(Hash Join)
작은 테이블로 해시 테이블을 만들고, 다른 테이블을 순회하며 매칭하는 방식.

#### 작동 방식
1. **빌드 단계(Build Phase)**: 작은 테이블에서 해시 테이블 생성. 각 행의 조인 키에 해시 함수 적용
2. **프로브 단계(Probe Phase)**: 다른 테이블의 각 행을 해싱하여 해시 테이블과 비교, 매칭되는 행을 조인 결과에 추가

- **시간 복잡도**: O(M+N)
- **성능**: 큰 데이터셋, 특히 두 테이블 크기 차이가 클 때 효율적
- **제약**: **동등(=) 조인에만 사용 가능**
- 메모리 부족 시 성능 저하 가능

### 조인 알고리즘 비교 요약
| 알고리즘 | 시간 복잡도 | 적합한 상황 |
|----------|-------------|-------------|
| 중첩 루프 | O(M*N) | 소규모 데이터셋 |
| 정렬 병합 | O(M log M + N log N) | 이미 정렬된 데이터, 비등가 조인 |
| 해시 | O(M+N) | 큰 데이터셋, 등가 조인 |
